# Phase 10 — Live BlueZoo Adapter

## Goal

Build a real `AudienceDataSource` that talks to BlueZoo's actual API and produces the same `BlueZooVisitInterval`-shaped data Phase 9's fixtures produce, so the join logic built there works unchanged against real data.

## Update: Bill's ad-play-tracking design (see Phase 9) specifies exactly how this adapter gets called

Per Bill's email (full text in `.docs/.context/project_context.md`), the live-mode flow is an **end-of-day batch reconciliation job**: for each `AdPlayRecord` delivered by the retailer's CMS that day, call this adapter with `(screen_id, start_time, end_time)` to get that specific ad-play's impressions. This is simpler than a continuous real-time integration — it's a scheduled batch job, not a live stream — but it does mean this adapter needs to answer accurately for **arbitrary, possibly sub-15-minute windows** (an ad play can be much shorter than BlueZoo's confirmed 15-minute historical grain). **This determines which BlueZoo endpoint to actually use**: the Real-time API (`get_occupancy_count`/`get_visits`) is the more likely fit for querying an exact ad-play window, versus the Data Warehouse `run_query` path, which is confirmed to operate at 15-minute grain for historical data. Verify this directly against BlueZoo's API/sandbox as part of step 2 below — it's a technical check, not a design decision, since Bill's design already specifies per-ad-play querying.

## This phase is blocked on an open question — read this before starting

BlueZoo has already publicly announced and open-sourced a very similar project: `github.com/bluezoo/ad-campaign-agent` (press release dated 2026-06-17), which references "Gemini Omni" and **BigQuery** — not the REST API at `api.bluezoo.io` this plan has otherwise been grounded against. This repo's own `README.md` also currently (over)states a BigQuery connectivity claim (corrected in Phase 1, item 6). **Confirm with Bill/Cid which integration path is real before writing adapter code**: BlueZoo's REST Data Warehouse API (`api.bluezoo.io`, documented, `AccessKey` auth, SELECT-only `run_query`) or a BigQuery dataset-share arrangement — these imply meaningfully different adapter code. This corresponds to open questions 1 and 2 in `99-open-questions-for-bill.md` (repo relationship and REST-vs-BigQuery, respectively — cross-referencing the global numbering there, not the local list at the bottom of this file).

## Current state

- No BlueZoo integration code exists anywhere in `app/` today (confirmed via repo-wide grep for `bluezoo`, `AccessKey`, `sensor_visits`, etc. — zero hits outside this plan's own docs).
- BlueZoo's REST API (confirmed via direct doc fetch, `https://api.bluezoo.io/#89e2277d-43ef-424b-b4d6-6f473538f108`) exposes:
  - **Data Warehouse API**: `list_tables`, `desc_table`, `run_query` (server-side **SELECT-only** — no DML/DDL possible even if a query tried; this meaningfully reduces the injection/write-safety surface the original plan was concerned about). Auth via `Authorization: AccessKey {{key}}` header.
  - **Real-time API**: `get_occupancy_count`, `get_visits` — lower-latency, narrower-purpose endpoints, likely a better fit than `run_query` for anything needing near-real-time numbers rather than historical aggregation.
  - Relevant tables: `sensor_visits` (impressions; **historical visit data has a confirmed 15-minute grain** — see Phase 9's correction, and note BlueZoo's own count field is `incoming_inner_count`, which is a floating-point value, not necessarily an integer — this app's `video_metrics` schema currently assumes integer impressions (`app/database/db.py:143`), a type mismatch to resolve explicitly rather than silently truncate), `sensor_visitors` (occupancy — distinct metric from visits, do not conflate), `sensor_dwell` (a **distribution of visit-duration bins**, not a scalar — see Phase 2's corrected glossary entry), `group_uv_*` (unique visitors) — do **not** use `sensor_pulses` (sensor telemetry/health, not audience data) or naively reuse the `campaign_id` field from `group_flow_transition/correlation/duration/segmentation` (BlueZoo's own "flow campaign" concept, unrelated to this app's ad campaigns).
  - The old Fetch API is discontinued (2025-12-31) — do not build against it or any documentation that still references it.
- Bill's own framing of this request (per the original email) was to "isolate live-vs-**cached**" data source code — not "live-vs-demo." That word choice matters: it implies the intended non-live path is a cache of *real* BlueZoo data (captured once, replayed deterministically), not necessarily a purely synthetic generator. Phase 9's fixtures are a reasonable placeholder, but review flagged that pure synthetic fixtures don't actually prove a real BlueZoo payload and a cached/live payload are interchangeable through this app's code. Step 3 below addresses this gap.

## Steps

1. **Resolve the open questions above with Bill/Cid before writing any adapter code.** This determines whether steps 2+ target the REST API or a BigQuery client.
2. Confirm (or define, if not already settled by Phase 9) the `BlueZooVisitInterval` DTO — sensor/screen ID, UTC timestamp/interval, `incoming_inner_count` (or equivalent), zone fields as required by BlueZoo's schema. Define an `AudienceDataSource` interface (a small `Protocol` or ABC) whose methods return this DTO, not a pre-aggregated `int`. **As part of this step, verify directly against BlueZoo's API/sandbox which endpoint actually answers a per-ad-play query correctly** — the Real-time API (`get_occupancy_count`/`get_visits`) for an exact, possibly sub-15-minute window, versus the Data Warehouse `run_query` path for 15-minute-grain historical aggregation. Bill's design (Phase 9) calls for querying per ad-play window directly, so this choice isn't optional — pick whichever endpoint actually supports that, and document why.
3. Implement three conformers to the same interface, not two: `SyntheticAudienceDataSource` (Phase 9's hand-shaped fixtures, for offline development with no BlueZoo account at all), `CachedBlueZooAudienceDataSource` (wraps a real, anonymized `sensor_visits` response captured once from an actual or sandbox BlueZoo account and replayed deterministically — this is what actually proves cached and live payloads are interchangeable, which pure synthetic fixtures cannot), and `LiveBlueZooAudienceDataSource` (real-time API/BigQuery calls per the resolved open question). If a real or sandbox BlueZoo account isn't available yet when this phase starts, implement the interface and `SyntheticAudienceDataSource` first, and add `CachedBlueZooAudienceDataSource` as soon as any real sample data is obtainable — do not skip it permanently, since it's the thing that actually validates the schema alignment Bill asked for.
4. Wire selection to Phase 5's `APP_MODE`: `demo` → `SyntheticAudienceDataSource` (or `CachedBlueZooAudienceDataSource` once available, if a cached-but-real experience is preferred for demos), `connected` → `LiveBlueZooAudienceDataSource`. **This is also where Phase 5's deferred fail-closed guard actually gets built** (see Phase 5's corrected scope) — the provider-selection factory introduced here is the first concrete place to raise a clear error for `connected` mode with missing/invalid credentials, rather than the placeholder guard the first draft of Phase 5 proposed building prematurely.
5. Handle BlueZoo → this-app screen/zone mapping explicitly: BlueZoo's sensors are keyed by their own zone/sensor IDs, which won't automatically match this app's `Screen` concept from Phase 9. Add a small, explicit mapping table/config (screen_id → BlueZoo sensor/zone ID) — this mapping is itself something Bill's team will need to provide per physical deployment. Note this is literally the "sensor/screen identifier" field in Bill's `AdPlayRecord` schema (Phase 9) — the CMS feed is expected to already carry whichever identifier this mapping resolves to, so confirm with Bill's team whether the CMS will emit BlueZoo's native sensor ID directly (no mapping needed) or this app's own screen ID (mapping needed).
6. **Minimum live-secret handling belongs in this phase, not deferred to Phase 12** (correction from review: putting real BlueZoo credentials through a bare `.env` file first and only migrating to proper secret management later is backwards — the first time this adapter runs against real credentials, it should already not be doing that). At minimum: read the `AccessKey` from an actual secret store (Google Secret Manager directly, or ADK's `SecretManagerClient` wrapper if it's genuinely simpler — verify the exact import path/signature against a pinned `google-adk` version before committing to the wrapper, since this hasn't been spiked yet) rather than a plaintext `.env` value, and default any `APP_MODE=connected` deployment to authenticated-only (not public) from the start. Never hardcode or commit the AccessKey. The richer identity/audit/signed-URL work stays in Phase 12 — this step is only "don't put a real credential somewhere careless from day one."
7. Add the operational concerns a real HTTP/data adapter needs (missing from the first draft of this phase): request timeout and retry/backoff policy, pagination/row-limit handling for `run_query`, explicit UTC normalization (and DST handling at day boundaries), a documented policy for BlueZoo's floating-point count fields vs. this app's integer-assuming schema, parameterized query construction (even though `run_query` is server-side SELECT-only, still avoid raw string interpolation), mapped/typed API error handling (4xx/5xx), and a stance on caching/staleness for repeated reads. A fixed, parameterized SELECT builder is sufficient here — this does not need a general-purpose query-sanitization framework, since `run_query`'s SELECT-only enforcement already removes the write-injection risk.

## Validation

- [ ] `SyntheticAudienceDataSource`, `CachedBlueZooAudienceDataSource`, and `LiveBlueZooAudienceDataSource` all pass the same contract test suite against the `AudienceDataSource` interface — the standard "provider conformance test" pattern. The synthetic/cached tests run with no live account required; a separate, clearly-labeled sandbox smoke test exercises the live adapter only when real credentials are available.
- [ ] With `APP_MODE=connected` and valid BlueZoo credentials, a real `run_query` (or `get_visits`) call returns data that flows correctly through Phase 9's join logic and Phase 3's `compute_rpi()`.
- [ ] With `APP_MODE=connected` and invalid/missing credentials, the app fails with a clear, specific error (not a generic exception, not a silent fallback to demo data) — this is the fail-closed principle deferred from Phase 5, now actually built and exercised here.
- [ ] Fixture tests cover: empty intervals, duplicate intervals, UTC day-boundary/DST cases, fractional (non-integer) visit counts, request timeout, and a retryable failure.
- [ ] Confirm zero use of `sensor_pulses` or the flow-analytics `campaign_id` field anywhere in the new adapter code.
- [ ] The `AccessKey` is read from a real secret store, not a plaintext `.env` value, in any `connected`-mode configuration used beyond a developer's own machine.

## Exit criteria

`APP_MODE=connected` produces real impressions data from BlueZoo, flowing through the exact same join/RPI logic the demo path uses, with a documented screen-to-BlueZoo-sensor mapping, minimum secret handling in place, and a `CachedBlueZooAudienceDataSource` proving real payloads and synthetic fixtures are actually interchangeable through this app's code (not just asserted to be).
