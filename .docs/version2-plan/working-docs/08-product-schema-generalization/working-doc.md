## The two design decisions (owner gate)

### Decision 1 — campaign category vs product category (phase doc step 5 / open question 2)

- **Option A — controlled campaign-theme taxonomy, decoupled from product category. RECOMMENDED.** Keep the CHECK + `CAMPAIGN_CATEGORIES` as the small closed theme list they already are (summer/formal/professional/essentials/holiday *are* themes, not garment types); add one neutral bucket **`always-on`** to both; give `create_campaign()` an explicit optional `category` parameter validated against `CAMPAIGN_CATEGORIES` (invalid explicit value → structured error); keep the fashion `category_mapping` only as a default *suggestion* for unmapped-product-category cases the default becomes `always-on` — a deliberate bucket, not a silent lie. Product.category stays fully open text (any vertical), zero campaign-side coupling; matches the repo's CHECK-constraint idiom and Phase 2's parity test. **Cost to state plainly:** SQLite can't ALTER a CHECK, so adding `always-on` rebuilds the campaigns table for pre-existing DBs — accepted because the demo DB is disposable (`make reset-db`; Agent Engine DB is ephemeral); the phase doc's "additive migration" language was about the *products* table, which needs no change at all.
- **Option B — free-form campaign category (drop the CHECK).** Nothing to map ever, but destroys Phase 2's just-merged parity test/constant, invites case/typo drift, and re-conflates the two concepts the phase doc explicitly says not to conflate. Rejected.
- **Option C — keep everything, error on unmapped.** Zero schema change, but then a non-fashion product *cannot* create a campaign until someone edits a hardcoded dict — failing this phase's own exit criterion; C alone is not viable, and C-plus-whitelist is just Option A with worse ergonomics. Retained only as A's validation behavior for a *bad explicit* category argument.

### Decision 2 — the non-fashion proof vertical (open question 7, client-preference call)

99-open-questions Q7 (still open): BlueZoo's marketed verticals are OOH advertising, retail, hospitality, smart cities. Candidates:

- **A — premium beverage line (e.g. craft cold-brew / sparkling water). RECOMMENDED.** Zero semantic overlap with garments (no style/color/fabric/occasion — everything must flow through `attributes`, the strongest genericity proof); stays inside the retail/in-store-screen story the whole demo is built on (cooler-door/endcap screens); per-SKU PoS attribution maximally plausible for Phases 10/12; and beverage footage (condensation, pour, ice) is the most reliably gorgeous Veo class — product-only by nature, which is exactly Phase 9's new mode. Example attributes: flavor, volume_ml, packaging, serving_temperature, caffeine_mg, key_ingredients, dietary_tags, seasonal_availability.
- **B — QSR menu item.** Hospitality is a marketed BlueZoo vertical and menu boards are archetypal in-store screens, but "store" semantics read oddly until Phase 9 lands and combo/modifier pricing muddies the RPI story that is the demo's spine.
- **C — consumer electronics.** Weakest proof (color/style overlap with fashion columns) and the AI-video genre most prone to artifacts (device text/logos).

**Owner decision (2026-07-20, working-doc gate): none-of-the-above, broader** — the schema must serve *any retail vertical sellable on BlueZoo in-store screens*, and the fixture becomes a small **multi-vertical core test set** rather than a single proof vertical: 1–2 SKUs each across beverage, QSR menu item, consumer electronics, furniture, and home appliance (the "Target/Lowes/Walmart" range), all attributes-first. Product images for these fixtures are *referenced* (image_filename) but not generated in this phase — the owner's intent is that users either upload product photos or generate them via nano banana (image-model work = Phase 14a; the `generate_product_image`/`import_products_from_folder` tools = Phase 15, which can grow this core set into real imagery). This strengthens the genericity proof (five unrelated attribute vocabularies through one schema) at the same schema cost.

## Implementation approach

1. **`Product` model** (`app/models/product.py`, CreativeVariation's pattern): required `id: int`, `name: str`, `category: str` (open text), `image_filename: str`, `description: str` (mapped from the existing `details` column); optional `gcs_path`/`local_path`/`created_at`; `attributes: dict = {}` parsed from the `metadata` JSON column. `from_row(dict) → Product` and `to_row() → dict` (round-trip, per Phase 15's contract). On read, `attributes` = parsed metadata **minus** keys that are typed columns (so `pattern` and future vertical keys live there without duplication); legacy fashion columns fold INTO `attributes` when the typed column is set (fashion products get `attributes={style, color, fabric, occasion, pattern?}` — one uniform access path for consumers).
2. **Adapter migration:** `get_product()`/`list_products()` return `Product` (exit criteria: "retrieved via get_product() as a typed Product"); the enumerated ~15 consumer lines in `campaign_tools`/`video_tools`/`prompt_builders` migrate to attribute/`attributes` access in the same task, preserving `prompt_builders`' exact fallback semantics (style → category → literal), with a golden test pinning prompt text for a NULL-style fashion product before/after. The agent-facing `list_products` tool keeps its current dict output contract (built from the typed model). Dead `get_product_by_name()` is migrated too (same shape, one line) rather than left as a second unmigrated surface.
3. **Category resolution per Decision 1** (Option A assumed): `always-on` added to CHECK + `CAMPAIGN_CATEGORIES` (campaigns table rebuild noted in SETUP_INSTRUCTIONS), explicit optional validated `category` param on `create_campaign()`, mapping fallback → `always-on`, parity test extended, fresh tests for fashion-mapped/non-fashion-default/explicit-valid/explicit-invalid.
4. **Multi-vertical core test set** per Decision 2: `app/database/retail_products_data.py` — 6–10 SKUs spanning beverage, QSR, electronics, furniture, home appliance; attributes-first (no fashion columns), each with an `image_filename` reference (no image generation this phase — Phase 14a/15). Seeded additively for tests/fixtures only — the demo catalog stays fashion (Phase 15's `DEMO_DATASET` knob owns runtime selection; noted as amendment there).
5. **Amendments shipped with this branch:** 99-open-questions Q7 → answered: general retail, multi-vertical core test set, not a single vertical (+ tally line); 08 phase-doc open questions 1–2 → resolved with provenance; 02 item 5 → provenance note on the fallback resolution; 09 → name the vertical in steps 6–7 wording + note the create_campaign category param + the `:88` description coupling; 15 → step 3 contract confirmation + note that the multi-vertical core set is the seed Phase 15's image tools grow into real imagery (`DEMO_DATASET` note); 10:40 → `Product.id: int` confirmation.
6. **Self-service substrate (owner directive, 2026-07-20, post-gate):** the demo must support the vendor flow — "can you run MY product through it?" — without rebuilding anything. This phase therefore ships the db-layer write path for on-the-fly products: `insert_product(Product) -> Product` (typed, through `to_row()`), with image handling reference-only (persistence, retrieval, and campaign creation must all work when the referenced image file doesn't exist yet — vendor uploads or nano-banana generation attach imagery later via Phase 14a/15 tools that WRAP this function). Proven by an end-to-end on-the-fly test: never-seeded product in a never-seen vertical → insert → typed retrieval → campaign.
7. **Not touched:** products table schema (no ALTER needed — recorded as the "migration" outcome), `products_data.py`'s 22 fashion entries, README.md/DEMO_GUIDE.md, product CRUD tools (Phase 15), presentation_mode (Phase 9), campaign auto-description text (Phase 9).
