## Implementation approach

Port at file/function granularity (never bulk-copy), applying all five corrections in-flight:

1. **New package `app/demo_data/`** (phase doc's suggested home; import-light so Phase 11a's move behind the provider seam is a file relocation):
   - `seed.py` — the ported generator. Keeps the donor's sha256→`np.random.default_rng` mechanism, slot layout, realism constants, Dirichlet dwell, frequency buckets, flow transitions. Renames: `store` → `screen` throughout (`SeedConfig.screen_ids`, frames `screen_visits`/`screen_dwell`, `screen_id` columns); `campaign_id` → `ad_campaign_id` in every frame (correction #2); `minimum_/maximum_visitors_*` (correction #5); bin names regenerated in **HHMM** encoding with the `_0058_to_0100` boundary (correction #1). **Frames become lists of dicts, not DataFrames** (see dependency decision below). Keyed off this app's IDs: `ad_campaign_id` = `campaigns.id`, `screen_id` = `campaigns.id` as a documented 1:1 proxy (a campaign is one store/screen today; Phase 10's `Screen` swaps in later without changing the key mechanism).
   - `constants.py` — `DEMO_RPI = 0.05` (donor's effective constant), the **single** RPI constant on the demo path (correction #3 kills the second literal).
   - `derive.py` — the deliberately disposable derivation layer: aggregates a day's 48 screen-level frames into one `video_metrics` row per activated video. `impressions` = sum of `incoming_inner_count` **only** (correction #3), apportioned across the campaign's activated videos by deterministic sha-seeded per-video weights (so per-creative numbers differ but sum to screen totals); `dwell_time_seconds` = expected dwell from the day's bin distribution via a correct **HHMM** midpoint decoder (correction #1's decoder fix); `revenue` = video impressions × `DEMO_RPI` (flat — owner decision below); `circulation` = derived from `outgoing_outer_count` but **written and documented as provenance-flagged synthetic** (correction #4 — a demo convention, never a BlueZoo mapping); any stored/derived RPI via `compute_rpi()` only. Per-video-per-day assumptions live only here (Phase 10 deletes this file).
   - `BLUEZOO_MAPPING.md` — the one mapping table the naming policy requires: every table/frame rename, every column divergence, the UTC-day convention, provenance flags (circulation, journey duration), and the donor-revision pin per ported file.
2. **Windowing rule (phase-doc step 2):** one anchor date + one rule. Anchor = the date the demo DB is seeded, stored in a tiny new `demo_meta` table (`key TEXT PRIMARY KEY, value TEXT`). Rule: **every generation call fills the backward window `[anchor − 29, anchor]`** — identical at seed time (`populate_mock_data`) and activation time (`activate_video`); determinism + `INSERT OR IGNORE` on `UNIQUE(video_id, metric_date)` make overlapping regeneration a no-op, which is what eliminates the seed/activation discontinuity. `generate_additional_metrics(days=N)` becomes "advance the anchor by N days and fill the new dates for the campaign's activated videos" — the closest deterministic equivalent of its current forward-from-max semantics, and it keeps a multi-day-old demo DB refreshable. UTC dates throughout, per the convention.
3. **Swap all three call sites** (`mock_data.py:383`, `review_tools.py:169`, `review_tools.py:564`) to generator + derivation, then **delete both old `_generate_mock_video_metrics` implementations** (phase-doc step 6; grep must return zero hits).
4. **Port the donor tests** alongside (`tests/unit/test_demo_seed.py` + derivation tests), adapted to the corrected shapes.

**Dependency decision — numpy yes, pandas no (owner-approved 2026-07-17).** The donor needs numpy (`default_rng`, Dirichlet) and pandas (DataFrames). Recommendation: add `numpy` to `app/requirements.txt` and port frames as lists of dicts. Why: numpy is what makes the donor's per-value RNG logic port verbatim (determinism mechanism untouched — a stdlib rewrite would need a hand-rolled Dirichlet and re-derive every number); pandas buys nothing here (the consumer is a SQLite INSERT loop and a small aggregation — no DataFrame ops survive the port) and is a heavyweight addition to the Agent Engine deploy for demo data only. Rejected: (a) add pandas too — closest to donor but dead weight; Phase 11a can add it if the provider port truly needs it; (b) pure stdlib — no new dep, but re-implements Dirichlet and forfeits verbatim-port confidence for marginal gain.

**Owner decision (2026-07-17): strict flat constant.** The flat-RPI tension was flagged (revenue = impressions × DEMO_RPI makes RPI identical, 0.05, for every video — top-ads-by-RPI rankings degenerate and Phase 7's RPI-across-creatives chart would be flat) and the owner chose the phase doc's letter: **flat constant now, revisit in Phase 7**. No per-video revenue factor. Per-video impressions still differ (deterministic apportionment), so impression/revenue *magnitudes* vary across creatives — only the RPI ratio is constant. Phase 7's doc is amended with a provenance note so its kickoff plans for this.
