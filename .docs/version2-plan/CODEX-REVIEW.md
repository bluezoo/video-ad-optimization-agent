# Adversarial review of the Version 2 plan

> **Note (2026-07-16):** phase numbers in this review were mechanically updated when the plan moved to 1-based numbering (phase number = doc filename prefix, workstream replan-data-track). Content is otherwise unchanged from the original review.

This plan is **not ready to be treated as final**. Its incremental direction is sound, Phase 1 is genuinely urgent, and many cited code defects are real. However, several current-state claims are incorrect, the sequencing table contains wrong dependencies and open-question numbers, Phase 10's synthetic schema is not structurally equivalent to BlueZoo's real 15-minute visit data, Phase 9 does not cover all of the fashion assumptions it promises to remove, and Phase 14b describes an experimental Interactions API as stable/GA. These are repairable plan defects, not reasons to rewrite the application: revise the affected phases, define one canonical BlueZoo-shaped cached/live contract, and retain the small-step rollout.

## Unverified/hallucination-risk claims

- **[blocking] [`10-playout-attribution.md` — Steps 3-4/Exit criteria](.docs/version2-plan/10-playout-attribution.md:11), [`11-live-bluezoo-adapter.md` — Current state/Steps](.docs/version2-plan/11-live-bluezoo-adapter.md:11), and [`03-metrics-glossary-and-terminology.md` — BlueZoo definitions](.docs/version2-plan/03-metrics-glossary-and-terminology.md:22): the public BlueZoo facts were independently verified, but the plan draws a load-bearing conclusion they do not support.** The official [BlueZoo API Suite](https://api.bluezoo.io/) does document `Authorization: AccessKey`, SELECT-only `run_query`, `sensor_visits`, and `incoming_inner_count` as visits/impressions. It also says historical visits have a maximum 15-minute grain. `sensor_visitors_per_minute` is optional and reports occupancy, not visit events. Therefore, a synthetic per-minute visit series is not “structurally identical” to the live schema, and `get_visit_counts(screen_id, arbitrary_start, arbitrary_end) -> int` hides important row/timestamp/zone semantics. **Suggested fix:** independently confirm the exact enabled tables and schema with `list_tables`/`desc_table` on the client's account, then define the cached/demo DTO from actual `sensor_visits` rows: sensor ID, UTC slot timestamp, `incoming_inner_count`, and any required zone fields. Treat occupancy and visits as different types.
